# PipeL4 benchmarks

This project measures one request/response echo exchange over IPv4 loopback. Every benchmark case
uses one persistent connection with one exchange in flight. `GlobalSetup` starts the backend and,
where applicable, the proxy; creates the connection and processor instances; and validates a
preflight exchange. The measured method contains only the common request/response round trip.

## Routes

- `Direct`: client to the in-process echo backend.
- `RawPipeL4`: client to the raw proxy path to the backend.
- `ViaEmptyProcessorPipeline`: processor-enabled proxy path with no stages.
- `InternalProcessorPipeline`, `InternalFourStagePipeline`, and
  `InternalEightStagePipeline`: one, four, or eight internal input-backed identity stages in each
  direction.
- `BoundedInternalProcessorPipeline`: one internal input-backed identity stage in each direction
  using the normal production configuration path with 256 KiB per-direction logical and
  connection-wide physical budgets.
- `FsxProcessorPipeline` and `FsxFourStagePipeline`: one or four real compiled `.fsx`
  input-backed identity stages in each direction.
- `FsxGeneratedOutputPipeline`: one real compiled `.fsx` stage in each direction that copies input
  into the runtime-provided output writer.
- `FsxWithStateAccess`: one real compiled `.fsx` stage in each direction that publishes an `obj`
  once during processor construction and calls `GetOrAdd` with the same fixed key and cached
  factory on every non-empty invocation.
- `FsxWithCachedState`: the same publication and observable reference check, but the processor
  caches the reference returned during construction instead of accessing the registry per
  invocation.

The pass-through and state fixtures call `AppendInput` and create no generated byte array or
processor payload copy. The generated fixture copies each input segment directly into the span
returned by the runtime writer. The bounded route also reports observed logical and physical peaks
during setup; its processor-generated output metric is zero for the borrowed pass-through route.
That metric is not complete runtime copy accounting. All script routes use the public
`PipeL4.Plugins` API.

For each `.fsx` case, setup materializes the embedded fixture and calls `ScriptPipelineLoader`
before starting the proxy. The same normalized path is repeated for every configured stage and
both directions. Setup counts compiler calls and fails unless loader cache reuse reduces them to
one unique compilation. The stopwatch message printed by setup is an informational observation of
compilation, assembly loading, discovery, and immutable-definition construction; it is not part of
the latency measurement.

Payloads are 64 B, 4 KiB, and 1 MiB. Reads accumulate the expected byte count and do not assume
that TCP preserves write boundaries. `Logical MiB/s` counts the application payload once in each
direction; it does not count both TCP legs of a proxied route separately.

Historical SHA values identify the source revisions actually measured. Some are no longer reachable
from rewritten public master history. A rewritten master commit with the same Git tree can reproduce
the same tracked source state, but identical tracked content does not mean the original measurement
ran under the rewritten SHA. Historical side-branch revisions without equivalent master commits
cannot be checked out from a fresh master-only clone.

## Bounded transport observation: 2026-10-25

The bounded identity route was run in Release mode on Ubuntu 24.04.5, .NET 10.0.13, and
BenchmarkDotNet 0.15.8 on an Intel Core i5-8365U. The route used 256 KiB logical budgets per
direction and a 256 KiB connection physical budget. Setup observations were 128 B logical peaks
per direction for the 64 B payload, 8 KiB for the 4 KiB payload, and 128 KiB for the 1 MiB payload;
the physical peak was 128 KiB in all three cases and the borrowed pass-through copy count was zero.

The same-run ShortRun comparison (three warmups and three iterations) was:

| Payload | Unbounded mean / throughput / allocation | Bounded mean / throughput / allocation |
| ---: | ---: | ---: |
| 64 B | 77.26 us / 1.58 MiB/s / 5.3 KiB | 76.68 us / 1.59 MiB/s / 5.3 KiB |
| 4 KiB | 87.48 us / 89.31 MiB/s / 5.3 KiB | 81.65 us / 95.68 MiB/s / 5.3 KiB |
| 1 MiB | 1.894 ms / 1,055.78 MiB/s / 80.8 KiB | 1.914 ms / 1,045.16 MiB/s / 80.79 KiB |

The 99.9% confidence margins for bounded rows were 58.27 us, 31.56 us, and 5.459 ms; the
small-payload rows are host-sensitive and should be treated as directional observations, not
throughput claims. A separate Dry discovery run completed all three bounded cases (1.398 ms,
1.353 ms, and 45.349 ms); those cold-start values are not compared with ShortRun results.
BenchmarkDotNet warned that the 1 MiB ShortRun iteration is below its 100 ms recommendation, so
these are not production throughput estimates.

## Connection-state operations

`ConnectionStateBenchmarks` isolates steady-state access to an already published value. It reports
latency and managed allocations for `GetOrAdd` and `TryGet` without loopback transport noise. The
registry, fixed key, published `obj`, and delegate are created before measurement.

`ConnectionStateLifecycleBenchmarks` measures these exact cumulative boundaries:

- registry construction only;
- construction plus one fixed-key first publication;
- construction plus four fixed-key first publications;
- construction plus disposal of an empty registry; and
- construction, publication of four lightweight already-completing `IAsyncDisposable` values,
  and complete registry disposal.

Construction is deliberately a separate baseline so the publication rows do not imply that setup
is free. Keys, values, and delegates are fixed benchmark fields; disposal is awaited inside the
measured lifecycle operation.

```sh
dotnet run --project benchmarks/PipeL4.Benchmarks -c Release -- --filter '*ConnectionState*'
```

Copied bytes and logical/physical buffer memory are not applicable to this benchmark because the
connection-state registry neither contains nor owns pipeline byte buffers.

## Limitations

These scenarios do not measure connection startup, pipelined streaming throughput, or broad
concurrent-connection scaling. MemoryDiagnoser allocation results are managed bytes attributed to
the thread executing the benchmark method. Asynchronous proxy/backend work on other threads may
not be included, so these are not process-wide allocation totals. The logical-admission microbenchmarks use an empty
pipeline to isolate reservation and waiter overhead; they do not claim that logical accounting
introduces copies. Integration tests record copied-byte behavior (borrowed ranges remain
zero-copy), logical peaks, and physical reservations.

`CapacityDiagnosticsBenchmarks` keeps a persistent one-connection exchange and varies only the
normal parsed capacity and `RuntimeDiagnosticsEnabled` configuration. It uses `NullLogger`, one
internal identity stage per direction, 4 KiB and 1 MiB payloads, and `MemoryDiagnoser`. Preflight
and iteration cleanup validate exact response bytes, capacity limits, diagnostic zero semantics,
and final release. `ConcurrentForwardingBenchmarks` runs one or eight simultaneous persistent
bounded connections with the same payload pair and validates every connection's output and final
accounting. `BackpressurePressureBenchmarks` gates a deterministic in-memory runtime sink (no
loopback sockets) and checks that the push is suspended while logical occupancy remains live, then
resumes with identical bytes. It measures external gate time as part of the scenario; it is a
correctness/pressure probe, not a comparative throughput benchmark or socket latency claim.
`LogicalAdmissionBenchmarks.BoundedExhaustionAndResumption4KiB` is the
capacity-wait case and asserts a nonzero completed waiter count; the slow sink is not treated as
capacity waiting.

## Observability overhead and lifecycle review: 2026-10-21

### Lifecycle measurements: 2026-10-22

The historical forwarding tables in this section are retained as implementation deltas. They
compare `b6fc7bf` with `a96f504`, and `a96f504` changed both observability and cleanup/ownership
behavior. They must not be read as isolated observability-component overhead. The focused before /
after measurement below compares the current pre-change commit `1435302` with the source state
that applies the lazy cleanup-failure collection change.

The intervening history confirms the confounders: `f5b8e7f` and `098e8de` changed logical-retention
teardown, `68d7948` and `7e6557e` added and hardened physical-capacity ownership, `7ebc87f` added
activity metrics/snapshots, `2081d0e` corrected async timing and snapshot immutability, and
`a96f504` hardened accounting and cleanup. The historical total is therefore an implementation
delta across ownership, cleanup, and observability—not an instrumentation-only experiment.

The focused harness was added identically to both revisions. Each measured operation rents one
`MemoryPool<byte>` owner, pushes 4 KiB through a no-op sink and `StageCount` pass-through stages,
and disposes the resulting pipeline state. It performs no EOF operation and no second direction.
Therefore the measured invocation count is exactly `StageCount` (0, 1, 4, or 8); no TCP round-trip
invocation multiplier is assumed.

The TCP forwarding methods intentionally report allocation per completed exchange only. Their
read loop can split a payload into multiple chunks, so a round trip does not have a fixed
`2 * depth` processor-invocation count, especially at 1 MiB. No per-invocation forwarding number
is derived from those rows.

| Stage count | Actual invocations / push | Before `1435302` | After lazy collection | Change | Change / invocation |
|---:|---:|---:|---:|---:|---:|
| 0 | 0 | 96 B | 96 B | 0 B | n/a |
| 1 | 1 | 824 B | 696 B | -128 B (-15.5%) | -128 B |
| 4 | 4 | 2,576 B | 2,160 B | -416 B (-16.1%) | -104 B |
| 8 | 8 | 4,912 B | 4,112 B | -800 B (-16.3%) | -100 B |

Both focused runs used Release, .NET SDK 10.0.113 / .NET 10.0.13, BenchmarkDotNet 0.15.8, and
`ShortRun` (three warmups and three measured iterations). The benchmark project and harness files
were byte-for-byte identical in the detached pre-change clone and the comparison source state.

The reduction is the successful-path cost of not constructing empty cleanup-failure collectors.
The measured slope is 584 B per added stage before the change and 488 B after it; the avoidable
part is 128 B for the first invoked stage and about 96 B for each additional invoked stage in this
harness. These are per-push managed allocations, not a claim about a TCP round trip.

Two additional probes kept the other suspected sites unchanged. Inlining the local timing helper
did not change the allocation rows, so the helper remains in place and exact invocation duration
semantics are unchanged. Replacing `Seq.sumBy` with `for` traversal increased the four-stage and
eight-stage rows (2,232/4,280 B for sequence traversal and 2,328/4,504 B for indexed traversal,
versus 2,160/4,112 B with `Seq.sumBy`), so `Seq.sumBy` was retained; no optimization is claimed
there.

As a bounded forwarding cross-check, empty-pipeline current/baseline runs were interleaved
current → baseline → current → baseline for all three payloads. The 64 B and 4 KiB rows both
reported 976 B on the empty route in every run. The 1 MiB rows varied by TCP segmentation (about
7.5–7.6 KiB), so they are classified as noisy. A single bounded interleaved pair for the internal
four-stage route reported about 5.13 KiB after versus 5.8 KiB before for the small payloads; this
was not used as a latency attribution because the short run was noisy. The direct allocation
benchmark above is the authoritative allocation comparison.

### Runtime and lifecycle review

The successful invocation hot path is: admit input once; record invocation start with monotonic
`Stopwatch.GetTimestamp`; run the processor; count output provenance (`AppendInput` ranges and
generated output lengths, without scanning byte values); validate the result; release the
unretained prefix and commit the retained suffix; then publish success counters, duration, and
retained/output gauges. Inter-stage forwarding enumerates the output range list once to sum logical
bytes for the next stage; this is range-list enumeration, not byte scanning. Each metrics boundary
uses the existing per-pipeline lock, so synchronization is at input admission, invocation start,
successful validation/commit, and failure/cancellation commit. `GetSnapshot` takes the same lock,
copies stage values, and aggregates them; it does not inspect network buffers.

Physical accounting was reviewed at the actual lease boundaries. A new tracked input owner or
generated owner allocates one wrapper and performs the corresponding atomic connection-gauge update
on acquisition; disposal is guarded once and releases the gauge only after the underlying owner is
disposed successfully. Shared storage is counted once at its physical owner, while logical
`SegmentOwner` ranges retain/release references independently. Raw forwarding pays one pooled-array
lease per direction for the lifetime of the measured connection. There are no per-range owner
lookups and no observability-only reference counting.

Allocation classes are separated as follows: connection (listeners, sockets, runtime state),
direction (direction metrics and pipeline), stage (stage metric storage and processor), lease
(tracked-owner wrapper and capacity lease), invocation (existing task/state and output-range
objects), snapshot (the stage array plus list, doubled for a connection snapshot), and teardown
(cleanup-hardening exception collection and disposal state). Observability metadata is distinct from
existing network buffers, output ranges, task state, and cleanup allocations. The forwarding
differences between these revisions therefore cannot all be attributed to metrics: the later
revision also contains unrelated cleanup hardening.

The focused allocation benchmark confirms that the tracked-owner wrapper is present in the empty
pipeline baseline and is required to preserve physical-capacity ownership and exactly-once release;
it was not removed. The remaining per-stage slope is the existing invocation/task/output-range
state plus metric work. The timing-closure probe showed no measurable managed-allocation change,
and the range-sum probes regressed allocations, so neither is treated as an avoidable source. The
connection-state disposal collector remains teardown-only and was not changed as a successful-path
optimization.

Duration starts before `ProcessAsync` and stops after its awaited completion, so asynchronous
suspension is included. Success, processor failure, cancellation, and teardown paths publish one
duration consistently, and no timing history is retained.

The processor-pipeline and integration tests map to every requested exit invariant. Processor-pipeline tests cover
single/multi-stage ordering, output provenance, retained-suffix ownership, generated output,
physical accounting, failure/cancellation duration, EOF, teardown, detached snapshots, and bounded
concurrent snapshots. TCP integration tests cover bidirectional traffic, half-close/EOF, concurrent
connections, one slow connection not blocking another, processor/socket failure cleanup, and
application cancellation. Compiled-script integration tests cover `.fsx` observability, concurrent
connection snapshots, snapshot lifetime after teardown, and script failures. The bounded concurrent
scenarios were reused as correctness/performance sanity checks, not throughput benchmarks.

`docs/architecture.md` remains accurate: snapshots are detached aggregates, accounting is tied to
physical ownership, directions remain concurrent, and bounded logical admission does not add global
serialization or a new scheduler. The logical budget is directional, the physical budget remains
connection-wide, and production entry points retain unbounded compatibility limits.

### Allocation and runtime review

For both 64 B and 4 KiB, raw/internal/`.fsx` allocation is 608/1,744/1,792 B per operation. The
one-stage `.fsx` increment is therefore 48 B. Four internal stages allocate 3,520 B and four
`.fsx` stages allocate 3,712 B: the 192 B difference is exactly 48 B per stage. Generated output
allocates 1,952 B, 160 B more than the input-backed `.fsx` route. Large-payload allocation varies
with TCP read segmentation and is not used to infer per-invocation cost.

Source inspection accounts for the `.fsx` increment as the expected per-invocation
`ProcessorOutputAdapter` reference object plus script/core input and result struct conversion.
Synchronous `ValueTask` completion does not take the asynchronous task fallback. There are no
per-invocation reflection arrays, temporary payload arrays, sequence materialization, compilation,
discovery, configuration parsing, or processor construction. Constructor reflection occurs only
when a connection/direction/stage instance is created.

`ScriptProcessorAdapter.AppendInput` delegates directly to the core invocation output. The core
validates the range and appends a borrowed range backed by the existing runtime-owned segment; the
adapter introduces no payload copy. The generated fixture intentionally performs one copy into
runtime-owned output storage.

### Interpretation and limits

forwarding, diagnostics overhead, or concurrent scaling: those distributions are too wide or too

not arbitrary performance gates.

the measured benchmark method. Asynchronous proxy/backend work on other threads may not be
included, so these are not process-wide client/backend/proxy totals. Generated-output counters are

runtime-owned leases; they do not attribute arbitrary `.fsx` allocations to the physical budget.

the measured forwarding operations. Deadlock/cleanup timeouts are correctness guards and are not

unidirectional in-memory push with an externally controlled gate. The separate bounded
logical-admission case reports completed capacity waiters and zero stranded waiters after release.

#### Full-job interpretation

The largest observed paired point regression is +15.8% in the focused synchronous internal
diagnostics allocation probe; it is reproducible in that narrow probe and has unchanged measured
allocations. The largest TCP point regression is +8.4% for bounded 4 KiB diagnostics enabled versus
disabled, but it is not reproducible at decision-grade precision. The largest stable-looking Raw
point difference is +3.3% at 64 B, also within overlapping 99.9% confidence intervals. The typical
current-binary bounded-path difference for small Raw forwarding is low single-digit percent with
unchanged displayed allocations. No measured regression warrants a production optimization based
on these data: the available full jobs do not establish one. The 1 MiB diagnostics and concurrency
results remain limited by loopback scheduling, multimodal distributions, and short per-iteration
durations. The pressure results are limited by the externally released in-memory gate and short
per-iteration durations, not loopback TCP scheduling. Repeating the TCP cases on a less contended
host with longer iteration times would be needed for a stronger large-payload conclusion.

Generated BenchmarkDotNet artifacts remain ignored and were not added to the commit.
