# PipeL4 benchmarks

This project measures one request/response echo exchange over IPv4 loopback. Every benchmark case
uses one persistent connection with one exchange in flight. `GlobalSetup` starts the backend and,
where applicable, the proxy; creates the connection and processor instances; and validates a
preflight exchange. The measured method contains only the common request/response round trip.

## Routes

- `Direct`: client to the in-process echo backend.
- `RawPipeL4`: client to the raw proxy path to the backend.
- `ViaEmptyProcessorPipeline`: processor-enabled proxy path with no stages.
- `InternalProcessorPipeline`, `InternalFourStagePipeline`, and
  `InternalEightStagePipeline`: one, four, or eight internal input-backed identity stages in each
  direction.
- `FsxProcessorPipeline` and `FsxFourStagePipeline`: one or four real compiled `.fsx`
  input-backed identity stages in each direction.
- `FsxGeneratedOutputPipeline`: one real compiled `.fsx` stage in each direction that copies input
  into the runtime-provided output writer.
- `FsxWithStateAccess`: one real compiled `.fsx` stage in each direction that publishes an `obj`
  once during processor construction and calls `GetOrAdd` with the same fixed key and cached
  factory on every non-empty invocation.
- `FsxWithCachedState`: the same publication and observable reference check, but the processor
  caches the reference returned during construction instead of accessing the registry per
  invocation.

The pass-through and state fixtures call `AppendInput` and create no generated byte array or
processor payload copy. The generated fixture copies each input segment directly into the span
returned by the runtime writer. All use the public `PipeL4.Plugins` API.

For each `.fsx` case, setup materializes the embedded fixture and calls `ScriptPipelineLoader`
before starting the proxy. The same normalized path is repeated for every configured stage and
both directions. Setup counts compiler calls and fails unless loader cache reuse reduces them to
one unique compilation. The stopwatch message printed by setup is an informational observation of
compilation, assembly loading, discovery, and immutable-definition construction; it is not part of
the latency measurement.

Payloads are 64 B, 4 KiB, and 1 MiB. Reads accumulate the expected byte count and do not assume
that TCP preserves write boundaries. `Logical MiB/s` counts the application payload once in each
direction; it does not count both TCP legs of a proxied route separately.

Run the full suite in Release mode:

```sh
dotnet run --project benchmarks/PipeL4.Benchmarks -c Release -- --filter '*RawTcpForwardingBenchmarks*'
```

Run a smoke check of every benchmark case:

```sh
dotnet run --project benchmarks/PipeL4.Benchmarks -c Release -- --filter '*' --job Dry
```

Run the allocation-only processor-pipeline comparison:

```sh
dotnet run --project benchmarks/PipeL4.Benchmarks -c Release -- \
  --filter '*ProcessorPipelineAllocationBenchmarks*' --job short
```

Reports are written under `BenchmarkDotNet.Artifacts/`, which is ignored by Git.

## Connection-state operations

`ConnectionStateBenchmarks` isolates steady-state access to an already published value. It reports
latency and managed allocations for `GetOrAdd` and `TryGet` without loopback transport noise. The
registry, fixed key, published `obj`, and delegate are created before measurement.

`ConnectionStateLifecycleBenchmarks` measures these exact cumulative boundaries:

- registry construction only;
- construction plus one fixed-key first publication;
- construction plus four fixed-key first publications;
- construction plus disposal of an empty registry; and
- construction, publication of four lightweight already-completing `IAsyncDisposable` values,
  and complete registry disposal.

Construction is deliberately a separate baseline so the publication rows do not imply that setup
is free. Keys, values, and delegates are fixed benchmark fields; disposal is awaited inside the
measured lifecycle operation.

```sh
dotnet run --project benchmarks/PipeL4.Benchmarks -c Release -- --filter '*ConnectionState*'
```

Copied bytes and logical/physical buffer memory are not applicable to this benchmark because the
connection-state registry neither contains nor owns pipeline byte buffers.

## Limitations

These scenarios do not measure connection startup, pipelined streaming throughput, or broad
concurrent-connection scaling. Allocation results include the in-process client, backend, and
proxy workload rather than PipeL4 alone. Exact copied-byte ratios and logical/physical runtime
buffer-memory counters are not exposed and are not approximated here. A deterministic integration
test, rather than BenchmarkDotNet, supplies the limited concurrent-connection serialization check.

The focused harness was added identically to both revisions. Each measured operation rents one
`MemoryPool<byte>` owner, pushes 4 KiB through a no-op sink and `StageCount` pass-through stages,

### Runtime and branch-exit review

The successful invocation hot path is: admit input once; record invocation start with monotonic
`Stopwatch.GetTimestamp`; run the processor; count output provenance (`AppendInput` ranges and
generated output lengths, without scanning byte values); validate the result; release the
unretained prefix and commit the retained suffix; then publish success counters, duration, and
retained/output gauges. Inter-stage forwarding enumerates the output range list once to sum logical
bytes for the next stage; this is range-list enumeration, not byte scanning. Each metrics boundary
uses the existing per-pipeline lock, so synchronization is at input admission, invocation start,
successful validation/commit, and failure/cancellation commit. `GetSnapshot` takes the same lock,
copies stage values, and aggregates them; it does not inspect network buffers.

Physical accounting was reviewed at the actual lease boundaries. A new tracked input owner or
generated owner allocates one wrapper and performs the corresponding atomic connection-gauge update
on acquisition; disposal is guarded once and releases the gauge only after the underlying owner is
disposed successfully. Shared storage is counted once at its physical owner, while logical
`SegmentOwner` ranges retain/release references independently. Raw forwarding pays one pooled-array
lease per direction for the lifetime of the measured connection. There are no per-range owner
lookups and no observability-only reference counting.

Allocation classes are separated as follows: connection (listeners, sockets, runtime state),
direction (direction metrics and pipeline), stage (stage metric storage and processor), lease
(tracked-owner wrapper and capacity lease), invocation (existing task/state and output-range
objects), snapshot (the stage array plus list, doubled for a connection snapshot), and teardown
(cleanup-hardening exception collection and disposal state). Observability metadata is distinct from
existing network buffers, output ranges, task state, and cleanup allocations. Current-branch
forwarding differences therefore cannot all be attributed to metrics: the branch also contains
unrelated cleanup hardening.

The focused allocation benchmark confirms that the tracked-owner wrapper is present in the empty
pipeline baseline and is required to preserve physical-capacity ownership and exactly-once release;
it was not removed. The remaining per-stage slope is the existing invocation/task/output-range
state plus metric work. The timing-closure probe showed no measurable managed-allocation change,
and the range-sum probes regressed allocations, so neither is treated as an avoidable source. The
connection-state disposal collector remains teardown-only and was not changed as a successful-path
optimization.

Duration starts before `ProcessAsync` and stops after its awaited completion, so asynchronous
suspension is included. Success, processor failure, cancellation, and teardown paths publish one
duration consistently, and no timing history is retained.

The processor-pipeline and integration tests map to every requested exit invariant. Processor-pipeline tests cover
single/multi-stage ordering, output provenance, retained-suffix ownership, generated output,
physical accounting, failure/cancellation duration, EOF, teardown, detached snapshots, and bounded
concurrent snapshots. TCP integration tests cover bidirectional traffic, half-close/EOF, concurrent
connections, one slow connection not blocking another, processor/socket failure cleanup, and
application cancellation. Compiled-script integration tests cover `.fsx` observability, concurrent
connection snapshots, snapshot lifetime after teardown, and script failures. The bounded concurrent
scenarios were reused as correctness/performance sanity checks, not throughput benchmarks.

`docs/architecture.md` remains accurate: snapshots are detached aggregates, accounting is tied to
physical ownership, directions remain concurrent, and the runtime does not add global serialization,
exporters, limits, or backpressure. The follow-up changes only successful-path cleanup collection;
the range-sum probe was measured and deliberately retained, and no architectural or backpressure
change was introduced.

### Allocation and runtime review

For both 64 B and 4 KiB, raw/internal/`.fsx` allocation is 608/1,744/1,792 B per operation. The
one-stage `.fsx` increment is therefore 48 B. Four internal stages allocate 3,520 B and four
`.fsx` stages allocate 3,712 B: the 192 B difference is exactly 48 B per stage. Generated output
allocates 1,952 B, 160 B more than the input-backed `.fsx` route. Large-payload allocation varies
with TCP read segmentation and is not used to infer per-invocation cost.

Source inspection accounts for the `.fsx` increment as the expected per-invocation
`ProcessorOutputAdapter` reference object plus script/core input and result struct conversion.
Synchronous `ValueTask` completion does not take the asynchronous task fallback. There are no
per-invocation reflection arrays, temporary payload arrays, sequence materialization, compilation,
discovery, configuration parsing, or processor construction. Constructor reflection occurs only
when a connection/direction/stage instance is created.

`ScriptProcessorAdapter.AppendInput` delegates directly to the core invocation output. The core
validates the range and appends a borrowed range backed by the existing runtime-owned segment; the
adapter introduces no payload copy. The generated fixture intentionally performs one copy into
runtime-owned output storage.
