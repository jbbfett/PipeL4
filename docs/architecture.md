# Architecture

PipeL4 is experimental. This document records current decisions, not a stable specification.

## Data flow

```text
Client
  |
  v
C -> S processor pipeline
  |
  v
Configured backend
  |
  v
S -> C processor pipeline
  |
  v
Client
```

The two directions may run concurrently. Ordering inside each direction is preserved.

### TCP forwarding lifecycle

The raw forwarding baseline runs each direction independently with a runtime-owned pooled buffer.

The processor-enabled path is an internal, opt-in runtime path. It creates fresh directional processor chains for each connection, rents runtime-owned input memory, and transfers received bytes into the socket-independent pipeline executor. Its socket sink sends every segment without flattening the logical sequence and awaits consumption before pipeline memory is released.

The executable selects forwarding independently per direction. A direction without configured
scripts uses the raw forwarding path; a configured direction uses the processor executor. The two
directional operations remain separate tasks and neither waits for the other processor chain.

A normal EOF in one direction is propagated as a TCP send-side shutdown to the destination. The opposite direction remains active until it also reaches EOF, fails, or application shutdown is requested.

A transport failure aborts both sides of that connection so the sibling forwarding operation cannot remain blocked. Connection failures are isolated from the listener and other connections. Application shutdown stops accepting, cancels active connections, and waits for their resources to be disposed.

The processor contract represents upstream completion explicitly and preserves directional completion and buffer ownership. At socket EOF, the executor performs final processing and flushes its output before the destination send side is shut down. Processor failure, transport failure, and cancellation release pipeline-owned memory and use the same per-connection failure isolation as raw forwarding.

## Core

The runtime owns:

- TCP listeners and backend connections;
- connection lifecycle and cancellation;
- processor scheduling and ordering;
- pipeline memory;
- buffering and backpressure;
- memory accounting;
- plugin loading and diagnostics.

The core is protocol-agnostic and operates on byte streams.

## Processor model

Plugins form ordered stream processors. The runtime controls pipeline execution.

A processor observes currently available bytes from its own logical input stream, emits zero or more ordered byte ranges into the next logical stream, and may retain a suffix of its input for a future invocation. The runtime owns physical memory and may share it between logical stream stages while references remain active.

Each processor has a distinct logical input stream. One processor's output becomes the next processor's input; a downstream processor can release only its own logical input and cannot release input retained by an upstream processor. The pipeline does not use a shared global input cursor.

Each invocation receives a potentially segmented, read-only byte sequence and an indication of whether upstream has completed. Its result contains only the length of the suffix to retain. The length must be within the current input, so retention cannot describe disjoint ranges. Everything before the suffix is released after successful validation and cannot be requested again.

Returning does not by itself schedule another invocation. The runtime invokes the processor again only after appending upstream bytes or observing upstream completion, passing the retained suffix together with the new input. When upstream is complete, a successful invocation must leave no retained bytes; it may emit or discard the final input, while processor-specific failure is represented by a faulted invocation.

Generated output is likewise limited to those runtime-triggered data or completion invocations. The current model has no timer, background producer, spontaneous-emission API, or processor-driven scheduling mechanism.

Output is an ordered combination of borrowed ranges from the current input and transformed or generated bytes written into runtime-owned storage. Borrowed ranges allow unchanged input to continue without a processor copy. Range boundaries have no downstream meaning and may be coalesced.

Output and retention are independent. A processor may emit and retain overlapping input, emit generated bytes while retaining all input, or retain bytes without emitting them. Downstream use of emitted data does not change the emitting processor's retained suffix. Output remains staged until the invocation succeeds and its retained suffix is validated; the runtime alone schedules downstream execution.

Each stage maintains an internal logical-retention gauge, `CurrentRetainedBytes`, equal to the
length of its currently committed retained suffix. The value is replaced after successful result
validation and suffix commitment; it is not cumulative and is owned by the stage whose logical
input contains the suffix. A stage may therefore retain bytes that are also emitted and retained
by another stage, and a sum across stages counts logical references rather than unique physical
storage. Snapshots expose the last committed value while an asynchronous invocation is pending.
Invalid results, processor failures, cancellation, and teardown do not publish speculative values;
entering terminal teardown clears live gauges before physical pending ranges are released, so a
snapshot either precedes that transition or observes zero even while physical cleanup is still in
progress. Snapshots do not retain completed connection objects. This accounting is observational
and does not alter processor execution, scheduling, or buffer ownership.

Each stage also maintains cumulative activity counters. `InputBytes` is an input-admission counter:
it counts each new logical byte occurrence when it enters that stage from its upstream stream.
Bytes already present in a retained suffix are not counted again when they are presented in a later
invocation, and an EOF invocation does not turn retained bytes into new input. The first stage
admits socket input; each later stage admits the successfully committed logical ranges transferred
from its upstream stage. This is not a successfully consumed-byte counter.

`InputBackedOutputBytes` counts the logical length of every successfully committed output range
borrowed from the current invocation input. `GeneratedOutputBytes` counts the logical length
advanced through the runtime-owned generated-output writer. The two counters are provenance-based,
not byte-value comparisons, and repeated emission counts each occurrence. They are published only
after result validation, output validation, and retained-suffix commitment; rented capacity,
tentative ranges, and output from a failed invocation do not count. Generated logical length is
independent from the physical capacity of its backing owner.

`InvocationCount` increases exactly once when execution of `ProcessAsync` begins. Completion
counters classify committed success, failure (including invalid processor results), and
cancellation caused by the requested invocation token. An active invocation may therefore be
present without a completion count. `ProcessingDuration` is cumulative elapsed wall-clock time for
completed invocation operations, measured with monotonic `Stopwatch` timestamps and represented as
`TimeSpan`; it includes asynchronous suspension and is not CPU time, downstream latency, or socket
write time.

Internal direction snapshots identify the `client-to-backend` or `backend-to-client` direction,
preserve configured stage order, expose the stage snapshots, and provide sums of the stage activity
and logical-retention fields. Those sums describe logical stage traffic and logical references;
they must not be interpreted as unique network traffic. A connection snapshot contains both
direction snapshots and `CurrentPhysicalBufferCapacityBytes` from the existing connection-level
lease accounting. It does not infer TCP socket byte counts or derive physical capacity from stage
metrics. A direction with no configured processors is represented by an empty, zero-valued stage
snapshot.

Snapshots are detached read-only values. Their immutable stage lists and records contain counters
and value data only, so retaining one does not retain processor instances, directional pipelines,
connection state, or runtime-owned buffers. Each direction uses short-lived synchronization while
counters are updated or copied; the two directions and physical-capacity gauge are read independently.
Consequently, a live connection snapshot may combine values observed at slightly different instants,
but individual counters are non-negative and free from torn reads or lost updates. Snapshot
collection does not traverse byte buffers or hold a connection-wide execution lock.

Each accepted connection also owns a physical-capacity gauge,
`CurrentPhysicalBufferCapacityBytes`. It is the sum of the actual capacities of all distinct
runtime-owned buffer leases currently active for that connection. A lease is counted once when
the runtime acquires it and remains counted until its underlying owner is released or its pooled
array is returned. Logical ranges, retained suffixes, sequence segments, processor stages, and
socket writes may all reference one lease without increasing this value. A one-byte retained
suffix therefore keeps the full capacity of its backing owner accounted. The two directions share
the connection gauge and update it independently; a half-close releases only the resources of the
completed direction.

Physical snapshots are read-only atomic observations of the capacity gauge. They do not retain
owners, traverse stages, or establish a globally synchronized instant with logical-retention
snapshots. A concurrent read may observe either side of an acquisition or release, but it is
always a non-negative current-state value rather than a cumulative allocation total.

Invocations return a value task, so asynchronous suspension needs no result state. Input and output memory remain valid until the invocation completes, including across suspension. Processors must not retain that memory or the output object afterward.

The executor accepts runtime-owned input chunks and runs each direction as one ordered chain. Each stage keeps its own pending logical ranges. A successful invocation releases the prefix before its retained suffix; later upstream ranges join that suffix without copying bytes. A stage runs again only when its upstream adds bytes or completes. An empty chain passes its input directly to the output sink.

Input-backed output ranges retain references to the physical storage behind the current input. Generated output is written through the processor's synchronous buffer writer into runtime-owned storage. Both forms enter one ordered range list and look identical to downstream stages. Physical storage is released only after all retained input, downstream ranges, and in-progress sink writes have released their references. The sink's awaited write marks consumption at this executor boundary.

The executor stages output until an invocation succeeds and its retained suffix is valid. Final output from a stage reaches the next stage with upstream completion; the sink completes only after the last stage has finished. Processor or sink failure and cancellation stop the pipeline and release its owned memory. An active invocation must finish before its input and output memory can be released.

Generated output within one processor invocation has no asynchronous backpressure: a processor can commit output synchronously before returning. The executor awaits the downstream sink between input chunks and does not maintain an unbounded interstage queue, but buffering within an invocation remains a current limitation.

## Plugins

Plugins are F# `.fsx` scripts compiled on load.

All configured scripts are read, compiled, loaded, and discovered before the TCP listener begins
accepting connections. A startup failure in any configured script prevents listener startup.
Within one application run, normalized script paths share one compiled plugin definition even when
the same path appears repeatedly or in both directions. This cache is in-memory and lasts only for
that application run.

`PipeL4.Plugins` owns in-process script compilation and assembly loading. The host supplies a
controlled reference set consisting of the running .NET runtime, FSharp.Core, and the public
`PipeL4.Plugins` API; plugin-authored `#r`, `#I`, and `#load` directives are rejected rather than
used to expand that set. `PipeL4.Core` and compiler-service APIs are not script references.
Compiler outputs are isolated in a per-compilation temporary directory, loaded from memory into
the default assembly load context, and then removed. Assemblies loaded this way remain present
for the process lifetime; unload and reload semantics are not part of the initial implementation.

The script-facing API mirrors the established processor semantics without exposing the internal
executor. An invocation receives a `ReadOnlySequence<byte>` and upstream-completion flag, emits
borrowed input ranges through `AppendInput`, writes generated bytes through an
`IBufferWriter<byte>`, and returns only a retained-suffix length in a `ValueTask`. A thin adapter
maps this API onto the existing core processor contract, so scripts use the same scheduling,
range validation, EOF validation, cancellation, ordering, and runtime-owned storage as internal
processors. The invocation input, output object, and uncommitted writable memory remain valid
across asynchronous suspension. Advancing writable memory commits it to the runtime, after which
the plugin must not use it; no invocation memory or output object may be retained after completion.

Each compiled script must contain exactly one visible, concrete, non-generic class that implements
`PipeL4.Plugins.IByteStreamProcessor` and has either a public parameterless constructor or a public
constructor accepting `PipeL4.Plugins.IConnectionState`. The state-aware constructor is preferred
when both are present. Discovery uses the explicit processor interface rather than compiler-generated
script type names. Construction is deferred until a connection's directional pipelines are created.
A constructor failure terminates only that connection, disposes any stages already constructed for
it, and does not invalidate the reusable compiled definition. Every configured stage receives a
fresh processor instance for each connection direction; compiled definitions and their constructor
metadata are reused, but mutable processor instances are not shared across connections, opposite
directions, or repeated stages.

When a directional pipeline ends, its processor instances are disposed in reverse stage order.
Processors may implement the standard `IAsyncDisposable` or `IDisposable` interfaces for their own
resources; asynchronous disposal is preferred when both are present. Runtime-owned input and output
memory is released independently of whether plugin cleanup succeeds.

Initial plugin environment:

- standard .NET/F# libraries;
- PipeL4-provided APIs;
- no unrestricted package loading.

Plugins are trusted code. Security and side effects are the plugin author's responsibility.
Execution cancellation is cooperative, and disposal must likewise complete cooperatively: code
that ignores cancellation or blocks a thread indefinitely cannot be safely preempted by PipeL4 and
may prevent bounded shutdown.

Plugins may observe, transform, drop, delay, buffer, frame, and maintain protocol state.

## State

The runtime creates exactly one internal connection-state registry for every accepted TCP
connection, including connections that use only raw forwarding. The per-connection processor
factory receives that registry once, so every stage in both directions can be associated with the
same instance. Registries are never shared between connections. `PipeL4.Plugins` creates one
non-owning `IConnectionState` view of that registry per connection and passes the same view to every
state-aware script processor constructor in both directions. The processor invocation signature is
unchanged, and parameterless processors do not need state-related boilerplate.

Processor instance fields remain the natural place for stage-local state. The runtime does not
provide additional per-stage, per-direction, per-plugin, per-listener, or process-wide registries.

Connection state uses ordinal string keys and exact declared .NET types. A key publishes at most
one value through thread-safe `GetOrAdd` initialization; concurrent first access executes the
published key's factory once. A factory failure is propagated and cached for the remainder of the
connection, without publishing or owning a partial value. `TryGet` can query a missing key without
adding one, and accessing a published key through a different type is an error. Independently
compiled scripts can share standard .NET types or another type with common CLR identity; types
declared separately in different script assemblies are incompatible even when structurally alike.

The registry guarantees thread-safe operations and safe publication, but it does not make mutable
stored values thread-safe. The two traffic directions remain concurrent, and no ordering between a
write in one direction and a read in the other is implied. State changes are not transactional with
processor execution and are not rolled back if an invocation later fails. State access and mutation
do not schedule processor execution or otherwise trigger pipeline processing.

Successfully published values are connection-owned. The registry remains alive after either
direction half-closes and is released only after both directional operations, final EOF processing,
active invocations, and processor cleanup have ended, or after whole-connection termination. Owned
values are disposed sequentially in reverse publication order, preferring `IAsyncDisposable` over
`IDisposable`; duplicate references are disposed once, and one cleanup failure does not skip other
values. Beginning disposal atomically closes the registry to new operations, which fail rather than
recreating state. Operations admitted before that transition, including an in-progress factory,
are allowed to finish before owned values are collected and disposed.

Connection state is independent from retained pipeline input and generated output. It neither owns
network buffers nor participates in logical or physical byte-memory accounting.

## Memory

Pipeline memory is runtime-owned. Plugins do not retain or release network buffers directly.

The runtime chooses suitable .NET memory primitives per execution path and may use spans, memory, sequences, or pools internally.

Logical stream ownership is separate from physical memory ownership. Multiple stages or purposes may reference the same runtime-owned segment, and the runtime may release or return that memory only after no logical reference still requires it.

Physical capacity accounting follows the runtime lease boundary, not the logical byte boundary. It
uses the actual capacity of raw `ArrayPool<byte>` arrays, processor input `IMemoryOwner<byte>`
leases, and generated-output owners rented from the processor pool. It does not use requested rent
size, received length, emitted length, or retained suffix length. Input-backed output reuses the
existing owner identity; generated output contributes a separate lease only when the runtime has
acquired storage for it. Physical buffer capacity accounting measures distinct active runtime-owned
storage leases. It does not discover or deduplicate arbitrary underlying allocations shared by
independent storage owners: shared references to one tracked lease count once, while independent
leases may refer to the same allocation in an allocator that permits that arrangement.

Returned pooled arrays are no longer active leases even if the pool keeps their storage cached for
future rents. Consequently this metric is not process RSS, GC heap usage, pool-reserved inactive
memory, total managed allocations, or complete plugin memory usage. Arbitrary arrays, dictionaries, and
other objects allocated by trusted plugins remain outside the metric; only plugin data copied into
runtime-owned output storage is counted through that destination lease.

If an underlying `IMemoryOwner.Dispose()` throws, the runtime cannot determine whether that owner
released its storage before throwing. The lease therefore remains conservatively accounted as active,
the owner is not retried, and the disposal exception is preserved. In that exceptional case the
physical-capacity gauge is an upper-bound accounting value rather than an exact measurement of
released storage.

This enables:

- centralized lifetime management;
- zero-copy paths where practical;
- controlled copying when required;
- cancellation/failure cleanup;
- backpressure;
- accounting by connection, direction, and plugin.

Diagnostics should distinguish:

- **logical buffered bytes** — data still required by processing;
- **active physical buffer capacity** — the full capacity of each distinct runtime-owned lease the
  runtime cannot yet release or return.

Arbitrary allocations made by plugin code are outside exact pipeline-memory accounting.

## Framing

TCP is a byte stream. Framing is plugin behavior, not a core protocol feature.

A processor may retain an unresolved input suffix until enough bytes arrive to identify a frame.

## Dependencies

PipeL4 is implemented in F# and uses Paket for project dependency management.

Paket manages dependencies of the application and development toolchain. It does not imply unrestricted runtime package loading for `.fsx` plugins; the plugin dependency boundary remains intentionally narrow for the initial implementation.

## Diagnostics

PipeL4 does not rewrite or automatically optimize plugin code at this stage.

Diagnostics may warn about blocking work, avoidable allocations, expensive sequence operations, excessive buffering, long processing times, and similar performance hazards.

## Open questions

- coalescing and copy-on-write behavior for borrowed output ranges;
- scheduling and fast paths between processors;
- buffering limits and fairness;
- plugin reload/unload behavior.
