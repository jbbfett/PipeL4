# Architecture

PipeL4 is experimental. This document records current decisions, not a stable specification.

## Data flow

```text
Client
  |
  v
C -> S processor pipeline
  |
  v
Configured backend
  |
  v
S -> C processor pipeline
  |
  v
Client
```

The two directions may run concurrently. Ordering inside each direction is preserved.

### TCP forwarding lifecycle

The raw forwarding baseline runs each direction independently with a runtime-owned pooled buffer.

The processor-enabled path is an internal, opt-in runtime path. It creates fresh directional processor chains for each connection, rents runtime-owned input memory, and transfers received bytes into the socket-independent pipeline executor. Its socket sink sends every segment without flattening the logical sequence and awaits consumption before pipeline memory is released.

The executable selects forwarding independently per direction. A direction without configured
scripts uses the raw forwarding path; a configured direction uses the processor executor. The two
directional operations remain separate tasks and neither waits for the other processor chain.

A normal EOF in one direction is propagated as a TCP send-side shutdown to the destination. The opposite direction remains active until it also reaches EOF, fails, or application shutdown is requested.

A transport failure aborts both sides of that connection so the sibling forwarding operation cannot remain blocked. Connection failures are isolated from the listener and other connections. Application shutdown stops accepting, cancels active connections, and waits for their resources to be disposed.

The processor contract represents upstream completion explicitly and preserves directional completion and buffer ownership. At socket EOF, the executor performs final processing and flushes its output before the destination send side is shut down. Processor failure, transport failure, and cancellation release pipeline-owned memory and use the same per-connection failure isolation as raw forwarding.

## Core

The runtime owns:

- TCP listeners and backend connections;
- connection lifecycle and cancellation;
- processor scheduling and ordering;
- pipeline memory;
- buffering and backpressure;
- memory accounting;
- plugin loading and diagnostics.

The core is protocol-agnostic and operates on byte streams.

## Processor model

Plugins form ordered stream processors. The runtime controls pipeline execution.

A processor observes currently available bytes from its own logical input stream, emits zero or more ordered byte ranges into the next logical stream, and may retain a suffix of its input for a future invocation. The runtime owns physical memory and may share it between logical stream stages while references remain active.

Each processor has a distinct logical input stream. One processor's output becomes the next processor's input; a downstream processor can release only its own logical input and cannot release input retained by an upstream processor. The pipeline does not use a shared global input cursor.

Each invocation receives a potentially segmented, read-only byte sequence and an indication of whether upstream has completed. Its result contains only the length of the suffix to retain. The length must be within the current input, so retention cannot describe disjoint ranges. Everything before the suffix is released after successful validation and cannot be requested again.

Returning does not by itself schedule another invocation. The runtime invokes the processor again only after appending upstream bytes or observing upstream completion, passing the retained suffix together with the new input. When upstream is complete, a successful invocation must leave no retained bytes; it may emit or discard the final input, while processor-specific failure is represented by a faulted invocation.

Generated output is likewise limited to those runtime-triggered data or completion invocations. The current model has no timer, background producer, spontaneous-emission API, or processor-driven scheduling mechanism.

Output is an ordered combination of borrowed ranges from the current input and transformed or generated bytes written into runtime-owned storage. Borrowed ranges allow unchanged input to continue without a processor copy. Range boundaries have no downstream meaning and may be coalesced.

Output and retention are independent. A processor may emit and retain overlapping input, emit generated bytes while retaining all input, or retain bytes without emitting them. Downstream use of emitted data does not change the emitting processor's retained suffix. Output remains staged until the invocation succeeds and its retained suffix is validated; the runtime alone schedules downstream execution.

Invocations return a value task, so asynchronous suspension needs no result state. Input and output memory remain valid until the invocation completes, including across suspension. Processors must not retain that memory or the output object afterward.

The executor accepts runtime-owned input chunks and runs each direction as one ordered chain. Each stage keeps its own pending logical ranges. A successful invocation releases the prefix before its retained suffix; later upstream ranges join that suffix without copying bytes. A stage runs again only when its upstream adds bytes or completes. An empty chain passes its input directly to the output sink.

Input-backed output ranges retain references to the physical storage behind the current input. Generated output is written through the processor's synchronous buffer writer into runtime-owned storage. Both forms enter one ordered range list and look identical to downstream stages. Physical storage is released only after all retained input, downstream ranges, and in-progress sink writes have released their references. The sink's awaited write marks consumption at this executor boundary.

The executor stages output until an invocation succeeds and its retained suffix is valid. Final output from a stage reaches the next stage with upstream completion; the sink completes only after the last stage has finished. Processor or sink failure and cancellation stop the pipeline and release its owned memory. An active invocation must finish before its input and output memory can be released.

Generated output within one processor invocation has no asynchronous backpressure: a processor can commit output synchronously before returning. The executor awaits the downstream sink between input chunks and does not maintain an unbounded interstage queue, but buffering within an invocation remains a current limitation.

## Plugins

Plugins are F# `.fsx` scripts compiled on load.

All configured scripts are read, compiled, loaded, and discovered before the TCP listener begins
accepting connections. A startup failure in any configured script prevents listener startup.
Within one application run, normalized script paths share one compiled plugin definition even when
the same path appears repeatedly or in both directions. This cache is in-memory and lasts only for
that application run.

`PipeL4.Plugins` owns in-process script compilation and assembly loading. The host supplies a
controlled reference set consisting of the running .NET runtime, FSharp.Core, and the public
`PipeL4.Plugins` API; plugin-authored `#r`, `#I`, and `#load` directives are rejected rather than
used to expand that set. `PipeL4.Core` and compiler-service APIs are not script references.
Compiler outputs are isolated in a per-compilation temporary directory, loaded from memory into
the default assembly load context, and then removed. Assemblies loaded this way remain present
for the process lifetime; unload and reload semantics are not part of the initial implementation.

The script-facing API mirrors the established processor semantics without exposing the internal
executor. An invocation receives a `ReadOnlySequence<byte>` and upstream-completion flag, emits
borrowed input ranges through `AppendInput`, writes generated bytes through an
`IBufferWriter<byte>`, and returns only a retained-suffix length in a `ValueTask`. A thin adapter
maps this API onto the existing core processor contract, so scripts use the same scheduling,
range validation, EOF validation, cancellation, ordering, and runtime-owned storage as internal
processors. The invocation input, output object, and uncommitted writable memory remain valid
across asynchronous suspension. Advancing writable memory commits it to the runtime, after which
the plugin must not use it; no invocation memory or output object may be retained after completion.

Each compiled script must contain exactly one visible, concrete, non-generic class that implements
`PipeL4.Plugins.IByteStreamProcessor` and has a public parameterless constructor. Discovery uses
that explicit interface rather than compiler-generated script type names. Construction is deferred
until a connection's directional pipelines are created. A constructor failure terminates only that
connection, disposes any stages already constructed for it, and does not invalidate the reusable
compiled definition. Every configured stage receives a fresh processor instance for each connection
direction; compiled definitions and their constructor metadata are reused, but mutable processor
instances are not shared across connections, opposite directions, or repeated stages.

When a directional pipeline ends, its processor instances are disposed in reverse stage order.
Processors may implement the standard `IAsyncDisposable` or `IDisposable` interfaces for their own
resources; asynchronous disposal is preferred when both are present. Runtime-owned input and output
memory is released independently of whether plugin cleanup succeeds.

Initial plugin environment:

- standard .NET/F# libraries;
- PipeL4-provided APIs;
- no unrestricted package loading.

Plugins are trusted code. Security and side effects are the plugin author's responsibility.
Execution cancellation is cooperative, and disposal must likewise complete cooperatively: code
that ignores cancellation or blocks a thread indefinitely cannot be safely preempted by PipeL4 and
may prevent bounded shutdown.

Plugins may observe, transform, drop, delay, buffer, frame, and maintain protocol state.

## State

Formal plugin state scopes are not yet part of the public API. The current per-stage,
per-direction, per-connection processor-instance lifetime provides execution isolation only; it is
not the supported state model. A later design will define per-direction state and state shared by
both directions of one connection, including its concurrency requirements.

## Memory

Pipeline memory is runtime-owned. Plugins do not retain or release network buffers directly.

The runtime chooses suitable .NET memory primitives per execution path and may use spans, memory, sequences, or pools internally.

Logical stream ownership is separate from physical memory ownership. Multiple stages or purposes may reference the same runtime-owned segment, and the runtime may release or return that memory only after no logical reference still requires it.

This enables:

- centralized lifetime management;
- zero-copy paths where practical;
- controlled copying when required;
- cancellation/failure cleanup;
- backpressure;
- accounting by connection, direction, and plugin.

Diagnostics should distinguish:

- **logical buffered bytes** — data still required by processing;
- **physical reserved bytes** — memory the runtime cannot yet reuse or return.

Arbitrary allocations made by plugin code are outside exact pipeline-memory accounting.

## Framing

TCP is a byte stream. Framing is plugin behavior, not a core protocol feature.

A processor may retain an unresolved input suffix until enough bytes arrive to identify a frame.

## Dependencies

PipeL4 is implemented in F# and uses Paket for project dependency management.

Paket manages dependencies of the application and development toolchain. It does not imply unrestricted runtime package loading for `.fsx` plugins; the plugin dependency boundary remains intentionally narrow for the initial implementation.

## Diagnostics

PipeL4 does not rewrite or automatically optimize plugin code at this stage.

Diagnostics may warn about blocking work, avoidable allocations, expensive sequence operations, excessive buffering, long processing times, and similar performance hazards.

## Open questions

- coalescing and copy-on-write behavior for borrowed output ranges;
- scheduling and fast paths between processors;
- buffering limits and fairness;
- plugin reload/unload behavior.
